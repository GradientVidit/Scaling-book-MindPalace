## 1. Summed up Outline

| Generation                       | Main idea                               | What is distributed/sharded?                 | Primary trade-off                                                                          |
| -------------------------------- | --------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **Traditional DDP**              | Replicate the model on every rank       | Nothing                                      | Simple, but high memory redundancy                                                         |
| **ZeRO-1**                       | Shard optimizer state                   | Optimizer states                             | Lower memory, additional distributed management                                            |
| **ZeRO-2**                       | Shard optimizer state + gradients       | Optimizer states + gradients                 | Further memory reduction, more communication                                               |
| **ZeRO-3**                       | Fully shard model state                 | Optimizer states + gradients + parameters    | Major memory reduction, parameter communication required                                   |
| **FSDP1**                        | Native PyTorch fully sharded training   | Parameters + gradients + optimizer states    | Uses `FlatParameter`; communication/resharding becomes central                             |
| **FSDP2**                        | Per-parameter DTensor sharding          | Parameters + gradients + optimizer states    | Better composability and integration with PyTorch distributed abstractions                 |
| **HSDP**                         | Hierarchical sharding + replication     | Shards within groups, replicas across groups | Trades memory efficiency against communication and topology                                |
| **Multidimensional parallelism** | Combine multiple parallelism dimensions | FSDP + TP + PP + CP, etc.                    | Enables much larger models/workloads but increases scheduling and communication complexity |

## 2. Detailed Outline

| Date | Event | Why it matters |
|---|---|---|
| **Oct 2019** | **ZeRO paper** | Introduces a systematic approach to eliminating data-parallel memory redundancy by partitioning optimizer states, gradients, and, at the most aggressive stage, parameters. **ZeRO-1** shards optimizer states; **ZeRO-2** additionally shards gradients; **ZeRO-3** additionally shards parameters. ZeRO-3 establishes the key conceptual foundation for later fully sharded data-parallel systems. |
| **2020** | **DeepSpeed + ZeRO ecosystem** | Turns ZeRO from a research technique into practical large-scale training infrastructure, integrating memory-efficient sharding with a broader distributed-training system. This establishes an important software lineage alongside the later PyTorch/FSDP lineage. |
| **2021** | **FairScale FSDP** | Provides a PyTorch-oriented implementation of fully sharded training, heavily inspired by ZeRO-3. FairScale becomes an important bridge between the ZeRO research concept and the later native PyTorch FSDP implementation. |
| **Jul 2021** | **Meta publicly introduces FSDP** | Demonstrates FSDP as a practical large-scale data-parallel training approach in the Meta/FAIR ecosystem. FSDP shards model parameters across data-parallel workers and is designed to reduce per-device memory consumption. |
| **Mar 2022** | **PyTorch 1.11 — native FSDP prototype** | FSDP enters core PyTorch as a prototype, with the implementation heavily influenced by FairScale. AWS/PyTorch scaling experiments demonstrate feasibility for dense models with up to 1 trillion parameters; this should be understood as a scaling demonstration rather than implying routine production training of 1T-parameter models. |
| **Jun 2022** | **PyTorch 1.12 — FSDP Beta** | FSDP moves toward production use with broader sharding strategies, mixed-precision policies, transformer auto-wrapping, faster initialization, and improved large-model checkpoint/save capabilities. **Correction:** PyTorch 1.12 was released on June 28, 2022, rather than July. |
| **Oct 2022** | **PyTorch/XLA FSDP** | Extends FSDP-style sharding to TPU/XLA environments, demonstrating that the fully sharded approach is not limited to CUDA GPU training and can be adapted to other accelerator runtimes. |
| **2022–23** | **FSDP productionization** | FSDP matures beyond its initial prototype through improvements in initialization, auto-wrapping, mixed precision, CPU offload, checkpoint/state-dict handling, memory management, reliability, and integration with the wider PyTorch training ecosystem. |
| **Apr 2023** | **PyTorch FSDP scaling paper** | Documents FSDP as an industry-grade large-model training system, reporting strong scaling characteristics and near-linear TFLOPS scaling in the tested configurations. It also highlights the importance of co-design across FSDP, tensor representations, the dispatcher, CUDA memory management, and communication. |
| **2023** | **Distributed Checkpointing** | Distributed checkpointing becomes an important companion to sharded training because no individual rank necessarily owns the complete model state. PyTorch's distributed checkpointing infrastructure enables distributed save/load and supports changes in world size when restoring checkpoints. |
| **2023–24** | **HSDP / Hybrid Sharded Data Parallelism** | Introduces a hierarchical strategy that combines sharding within groups with replication across groups, allowing large clusters to trade off memory savings, communication volume, and network topology more flexibly than a single global sharding group. |
| **2024** | **FSDP2 / `fully_shard` emerges** | Introduces a new FSDP architecture based on DTensor and per-parameter sharding, replacing FSDP1's `FlatParameter` abstraction. This improves composability with other distributed tensor abstractions and makes sharding more naturally compatible with PyTorch's evolving distributed stack. |
| **2024** | **FSDP2 + compiler/communication co-design** | FSDP2 begins to be combined more deeply with DTensor, `torch.compile`, low-precision/Float8 computation, and optimized collective communication, showing that FSDP is increasingly becoming part of an integrated runtime/compiler/communication stack rather than an isolated memory-saving technique. |
| **2024–25** | **TorchTitan + multidimensional parallelism** | Large-scale LLM training increasingly combines FSDP/FSDP2 with tensor parallelism (TP), pipeline parallelism (PP), context parallelism (CP), HSDP, and distributed checkpointing. FSDP consequently evolves from a standalone data-parallel strategy into one dimension of a composable multidimensional parallelism system. |
| **2025–26** | **FSDP2 maturation and distributed-system integration** | FSDP2 increasingly serves as the newer PyTorch sharding architecture, with tighter integration with DTensor, compilation, mixed/low-precision computation, distributed checkpointing, topology-aware strategies, and other parallelism dimensions. The emphasis shifts from simply fitting larger models into memory toward optimizing the entire distributed training system. |
| **2025–26** | **Emerging flexible and structure-aware sharding research** | Current research increasingly explores more flexible sharding policies, structure/topology-aware partitioning, communication-efficient scheduling, broader optimizer support, and scaling distributed training across very large accelerator clusters. These should be treated as active research directions, not all as established FSDP production features. |
