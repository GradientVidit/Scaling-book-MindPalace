- Compute bound = $(T_\text{math}​>T_\text{comms​})$ or ($\text{Intensity}(\text{Computation}) > \text{Intensity}(\text{Accelerator})$)
- Communication bound = $(T_\text{math}​<T_\text{comms​})$ or ($\text{Intensity}(\text{Computation}) < \text{Intensity}(\text{Accelerator})$)

# Matrix Multiplication

## Matrix Shape

$$
X[B, D] \cdot Y[D, F] \rightarrow Z[B, F]
$$

where

- **B** = Batch size (number of input vectors/tokens processed together)
- **D** = Input (hidden) dimension
- **F** = Output (feature) dimension

---

## Compute Cost (FLOPs)

**Why?  This estimates how long the MXU/Tensor Core spends computing.

Each output element requires:

- \(D\) multiplications
- \(D-1\) additions

Approximate as:

$$
2D \text{ FLOPs}
$$

There are \(B x F\) output elements.

Therefore,

$$
\boxed{\text{Compute} \approx 2BDF \text{ FLOPs}}
$$

---

## Communication / Memory Traffic

**Why?  This estimates the minimum time required to move data from HBM.

Ignoring cache reuse (worst-case estimate):

Read input matrix:

$$
BD
$$

Read weight matrix:

$$
DF
$$

Write output matrix:

$$
BF
$$

Total elements communicated:

$$
\boxed{BD + DF + BF}
$$

If each element occupies \(s\) bytes (e.g., FP16 = 2 bytes, FP32 = 4 bytes):

$$
\boxed{(BD + DF + BF)\times s \text{ bytes}}
$$

---

## Arithmetic Intensity

$$
\text{Arithmetic Intensity}
=
\frac{\text{Compute}}{\text{Communication}}
=
\frac{2BDF}{BD + DF + BF}
\quad
\text{FLOPs/element}
$$

or, in bytes,

$$
\boxed{
\frac{2BDF}
{(BD + DF + BF)s}
\text{ FLOPs/byte}
}
$$
---
#### Common mistakes
- Arithmetic intensity tells you runtime. No.
	it only helps predict whether you'll be compute or memory-bound.

- **Increasing B or D increases data reuse, which increases arithmetic intensity and makes computation more likely to be compute-bound.**
		**However, on multi-chip systems, increasing D also increases communication, so the gains are smaller than on a single chip.**
